#### 최종 프롬프트 `vlm-v0.3.3` (E1 · E2 · E3-L 공통)

- `$` 자리는 리뷰마다 코드가 채움

| 자리 | 채우는 값 |
|---|---|
| `$domain` | 도메인 (Books · Fashion · Electronics · Edible) |
| `$title` | 리뷰 제목 |
| `$review` | 리뷰 본문 (1,500자에서 자름) |
| `$n_images` | 사진 수 (최대 4) |
| `$part_codes` | 그 도메인에서 쓸 수 있는 부위 코드 목록 |

**영어 원문 (모델에 실제로 들어가는 글)**

```text
Amazon India customer complaint ($domain).
Title: $title
Review: $review

The customer attached $n_images photo(s), shown above as Picture 1 to Picture $n_images.

Find the main complaint, check it against the pictures, and fill in the ANSWER FORM at the end.

CATEGORY LIST (the code is the text before the colon):
damage/tear_hole: torn, ripped, a hole
damage/crush_break: crushed, broken, cracked (incl. a cracked screen), dented
damage/scratch: scratched, scuffed
damage/opened_tampered: opened or tampered with before it arrived
contamination/pest: insects, worms
contamination/mold_spoil: mold, rotten or spoiled food
contamination/foreign_object: a foreign object (metal piece, staple pin, hair)
contamination/stain_dirt: stains, dirt
manufacturing/material: thin or cheap fabric, poor paper, pilling, dirty material
manufacturing/stitching: bad or loose stitching
manufacturing/print: smudged, faded or wrong print
manufacturing/color: colour defect (faded, uneven, bleeding)
manufacturing/display: display defect (backlight bleed, dead pixels)
manufacturing/assembly: badly assembled or glued
not_as_described/counterfeit_wrong: fake / not original, or a different product, size, colour or model than ordered
not_as_described/missing: a piece or item is missing
not_as_described/used: already used
not_as_described/label_expiry: expired
function/malfunction: does not work, stopped working, shows wrong output
function/performance: works badly (slow, weak, overheating)
function/fit_size: arrived as ordered but does not fit
function/design_usability: awkward design
non_visual/taste_smell: taste or smell
non_visual/content: the book or media content itself (story, characters, writing, information)
non_visual/service: delivery, refund, return, warranty, seller or customer support
non_visual/price: price or value for money
non_visual/vague: no concrete problem named ("bad product", "waste of money") and none shown

RULES
1. Main complaint: the complaint in the TITLE first; if the title has none, the one the body talks about most. Use only what the review states; if the text is vague but a picture shows a concrete defect, use that defect.
2. category: choose by the SYMPTOM, not a guessed cause. not_as_described ONLY when the item received differs from what was ordered or advertised; poor quality, "not as expected", or "not like the picture" because it looks cheap is NOT not_as_described.
3. part: where the problem actually is, one of these codes: $part_codes. Expired food -> contents. Size problems -> whole. Throwaway bag/box -> product_package; jar/bottle kept during use -> container. label/manual only if the label or manual itself is wrong or missing. Service/price -> none. No nameable part (overheating, slowness, colour) -> whole. A part not in the list -> other.
4. visibility: "localized" = the defect (or evidence such as an error message, an expired date, a cracked screen) shows in a specific spot of a picture; "diffuse" = visible but over the whole product (colour, fit, generally thin material, a counterfeit that looks clearly different); "not_visible" = everything else (function, taste, service, content, missing items, unrelated photo, a counterfeit that looks identical). Size tags, price tags and manual numbers are not evidence.
5. boxes: only if visibility is "localized", otherwise []. 1 to 3 tight boxes around the defect, all on the ONE picture where it shows best. bbox_2d = [x1, y1, x2, y2] in that picture's pixel coordinates; a box must be clearly smaller than the picture. label = a few words naming what is inside the box. target = "defect" if the defect itself is visible (a hole, an insect, smudged print) or "evidence" if it is a sign that proves the problem (an error message, an expired date).

EVIDENCE: keep what the customer says apart from what the pictures show. Write the free-text fields in Korean (한국어), except review_span.
- customer_claim: one Korean sentence that starts with "고객은" and ends with "주장함", stating what the customer claims. Keep claims about when or how it happened (for example "arrived torn"), but never state them as facts.
- review_span: the exact words from the title or review that state the main complaint, copied without any change (English, at most 20 words).
- visual_findings: for each picture that shows something related, one Korean sentence on what is actually visible (where it is, its shape or colour). Describe the picture, not the review. If no picture shows the problem, give one entry for picture 1 saying so. box_ref = the number of the matching box in "boxes" (1 for the first box), or null.
- claim_support: "supported" only if a picture itself shows evidence for the main claim (the customer's words are not evidence); "partially_supported" if pictures show only part of it; "not_verifiable" if pictures cannot show it (this does NOT mean the claim is false); "contradicted" only if a picture clearly conflicts with the claim.
- limitations: 1 or 2 short Korean notes on what the pictures cannot confirm about THIS complaint (for example, when it happened, or whether it works). Write only notes that matter for this complaint. Do not guess causes.

ANSWER FORM. Reply with this JSON object only, with no other text. Keep every key, in this order. Replace each <...> with your answer; where options are separated by |, write exactly one of them. Use codes exactly as written above; never invent a new code.
{"category": "<one code from the CATEGORY LIST>",
 "part": "<one allowed part code>",
 "visibility": "localized|diffuse|not_visible",
 "boxes": [{"picture": <picture number>, "bbox_2d": [<x1>, <y1>, <x2>, <y2>], "label": "<what is in the box>", "target": "defect|evidence"}],
 "evidence": {"customer_claim": "<한국어 한 문장>",
              "review_span": "<exact words from the title or review>",
              "visual_findings": [{"picture": <picture number>, "description": "<한국어 한 문장>", "box_ref": <box number or null>}],
              "claim_support": "supported|partially_supported|not_verifiable|contradicted",
              "limitations": ["<한국어 짧은 메모>"]}}
```

```text
아마존 인도 고객 불만 리뷰 ($domain).
제목: $title
리뷰: $review

고객이 사진 $n_images장을 첨부했고, 위에 Picture 1 ~ Picture $n_images로 있다.

주 불만을 찾고, 사진과 대조한 뒤, 맨 끝의 답 양식(ANSWER FORM)을 채워라.

분류 목록 (콜론 앞이 코드):
damage/tear_hole: 찢어짐, 뜯어짐, 구멍
damage/crush_break: 눌림, 깨짐, 금 감 (화면 금 포함), 찌그러짐
damage/scratch: 긁힘, 쓸림
damage/opened_tampered: 도착 전에 개봉됐거나 손댄 흔적
contamination/pest: 벌레, 애벌레
contamination/mold_spoil: 곰팡이, 썩거나 상한 음식
contamination/foreign_object: 이물질 (쇳조각, 스테이플 핀, 머리카락)
contamination/stain_dirt: 얼룩, 때
manufacturing/material: 얇거나 싸구려 원단, 나쁜 종이, 보풀, 더러운 소재
manufacturing/stitching: 불량하거나 풀린 바느질
manufacturing/print: 번지거나 바래거나 잘못된 인쇄
manufacturing/color: 색 불량 (바램, 얼룩덜룩, 이염)
manufacturing/display: 화면 불량 (빛샘, 불량 화소)
manufacturing/assembly: 조립 · 접착 불량
not_as_described/counterfeit_wrong: 가짜 / 정품 아님, 또는 주문과 다른 제품 · 사이즈 · 색 · 모델
not_as_described/missing: 부품이나 물건이 빠짐
not_as_described/used: 이미 사용한 것
not_as_described/label_expiry: 유통기한 지남
function/malfunction: 작동 안 함, 작동이 멈춤, 잘못된 출력
function/performance: 작동이 나쁨 (느림, 약함, 과열)
function/fit_size: 주문대로 왔지만 안 맞음
function/design_usability: 불편한 설계
non_visual/taste_smell: 맛이나 냄새
non_visual/content: 책 · 미디어 내용 자체 (줄거리, 인물, 글, 정보)
non_visual/service: 배송, 환불, 반품, 보증, 판매자 · 고객 지원
non_visual/price: 가격 또는 가성비
non_visual/vague: 구체적인 문제를 말하지 않았고 ("나쁜 제품", "돈 낭비") 사진에도 안 보임

규칙
1. 주 불만: 제목의 불만이 먼저. 제목에 없으면 본문에서 가장 많이 말한 것. 리뷰에 적힌 것만 쓴다. 글은 모호한데 사진에 구체적인 결함이 보이면 그 결함을 쓴다.
2. category: 추측한 원인이 아니라 증상으로 고른다. not_as_described는 받은 물건이 주문 · 광고한 것과 다를 때만. 품질이 나쁨, "기대와 다름", 싸 보여서 "사진과 다름"은 not_as_described가 아니다.
3. part: 문제가 실제로 있는 곳, 다음 코드 중 하나: $part_codes. 유통기한 지난 음식 -> contents. 사이즈 문제 -> whole. 버리는 봉지/상자 -> product_package, 쓰는 동안 두는 병/통 -> container. label/manual은 라벨이나 설명서 자체가 틀리거나 빠졌을 때만. 서비스/가격 -> none. 이름 붙일 부위가 없음 (과열, 느림, 색) -> whole. 목록에 없는 부위 -> other.
4. visibility: "localized" = 결함(또는 에러 메시지, 지난 유통기한, 깨진 화면 같은 증거)이 사진의 특정 위치에 보임. "diffuse" = 보이지만 제품 전체에 퍼져 있음 (색, 핏, 전체적으로 얇은 소재, 확연히 달라 보이는 가짜). "not_visible" = 나머지 전부 (기능, 맛, 서비스, 내용, 빠진 물건, 관련 없는 사진, 똑같아 보이는 가짜). 사이즈 태그, 가격표, 설명서의 숫자는 증거가 아니다.
5. boxes: visibility가 "localized"일 때만, 아니면 []. 결함을 딱 맞게 감싼 박스 1~3개, 모두 결함이 가장 잘 보이는 사진 한 장에. bbox_2d = 그 사진의 픽셀 좌표로 [x1, y1, x2, y2]. 박스는 사진보다 확실히 작아야 한다. label = 박스 안에 있는 것을 몇 단어로. target = 결함 자체가 보이면(구멍, 벌레, 번진 인쇄) "defect", 문제를 증명하는 표시면(에러 메시지, 지난 날짜) "evidence".

근거(EVIDENCE): 고객이 말한 것과 사진에 보이는 것을 섞지 않는다. 자유 서술 칸은 review_span만 빼고 한국어로 쓴다.
- customer_claim: "고객은"으로 시작해 "주장함"으로 끝나는 한국어 한 문장으로, 고객이 주장하는 것을 쓴다. 언제 · 어떻게 생겼다는 주장(예: "찢어진 채 도착")은 남기되, 절대 사실처럼 쓰지 않는다.
- review_span: 주 불만을 말한 제목 · 리뷰의 정확한 문구를 하나도 바꾸지 않고 복사 (영어, 20단어 이하).
- visual_findings: 관련된 것이 보이는 사진마다, 실제로 보이는 것(위치, 모양이나 색)을 한국어 한 문장으로. 리뷰가 아니라 사진을 묘사한다. 문제를 보여 주는 사진이 없으면 사진 1에 대해 그렇다고 한 항목만 쓴다. box_ref = "boxes"에서 맞는 박스 번호 (첫 박스가 1), 없으면 null.
- claim_support: 사진 자체가 주 주장의 증거를 보여 줄 때만 "supported" (고객의 말은 증거가 아님). 사진이 일부만 보여 주면 "partially_supported". 사진으로 보여 줄 수 없는 것이면 "not_verifiable" (주장이 거짓이라는 뜻이 아님). 사진이 주장과 확실히 충돌할 때만 "contradicted".
- limitations: 이 불만에 대해 사진으로 확인할 수 없는 것을 짧은 한국어 메모 1~2개로 (예: 언제 생겼는지, 작동하는지). 이 불만에 중요한 것만 쓴다. 원인을 추측하지 않는다.
```

## 6. 왜 이렇게 했나 · 결과 해석

### 공통 원칙

- **공식 방식 그대로**: Qwen 모델 카드의 추론 방식과 HAWK 저장소 코드를 고치지 않고 씀. 우리가 바꾼 건 프롬프트와 출력 JSON뿐 → "원래 모델이 우리 과제에서 어디까지 되나"를 공정하게 잼
- **LLM만 4비트**: 7B를 bf16으로 올리면 가중치만 16.6GB라 16GB GPU에 안 들어감. Qwen 공식 4비트판처럼 비전 인코더는 bf16으로 둠
- **한 번에 하나만 바꿈**: E2는 HAWK만, E3-L은 어댑터만. 그래야 지표 차이를 그 하나 때문이라고 말할 수 있음
- **test는 마지막에 한 번**: 프롬프트는 정답 없는 dev로, 에폭은 val로 고르고, test는 설정마다 한 번만 돌림 → test 점수가 부풀려지지 않게

### E0 — 프롬프트 고르기

- **왜**: 제로샷은 학습이 없어서 JSON이 틀에 맞게 나와야 13지표를 잴 수 있음 (깨진 답은 모든 지표에서 오답). 정답을 보고 프롬프트를 고치면 점수가 부풀려지므로 정답 없는 dev에서 **형식만** 고침
- **해석**:
  - 첫 판(`v0.2`)이 24/30만 맞은 주원인은 공식 반복 벌점 1.05: 이 벌점이 **프롬프트에 적힌 토큰에도** 걸려서 모델이 목록의 라벨 코드를 피하고 `localizable` 같은 말을 지어냄
  - 벌점을 끄는 대신 출력 틀을 고침: 그룹/결함을 한 코드로 고르게 하고(`v0.3.1`), 박스 이름과 종류를 나누고, 부위는 코드만 나열(`v0.3.2`) → `v0.3.3`에서는 공식값 1.05로도 30/30. 벌점 1.0은 드물게 같은 말을 끝없이 반복해서 공식값을 유지함
  - 사진 크기를 알려 주면(`v0.3`) 그 숫자를 그대로 박스로 베껴서 버림
  - Prefill은 판이 바뀌어도 약 4초로 같고, E2E 차이는 출력 길이(근거 문장)에서 옴

### E1 — Qwen 제로샷

- **왜**: 학습 없이 공식 방식 그대로 돌린 결과가 이후 모든 실험의 기준선. 글만 보는 R0와 비교해 사진을 쓰는 의미가 있는지 확인
- **해석**:
  - **Group6 0.675로 R0(0.539)보다 높음** → 결함 종류를 고르는 데는 사진과 VLM이 도움이 됨
  - **Scope 0.376 · Visibility 0.507은 R0보다 낮음** → 모델이 "사진에 보인다"고 과신함 (val에서 정답 not_visible 38건 중 29건을 보인다고 답함). 서비스 · 가격 불만에도 제품 부위를 붙여서 Scope가 낮음
  - Grounding: Pointing 0.50이지만 IoU@0.5는 0.18 → 박스 중심은 절반쯤 맞는데 박스 크기 · 모양은 대부분 안 맞음
  - E2E 10.6초 중 Prefill은 2.0초뿐이고 나머지는 근거 문장을 쓰는 디코딩

### E2 — E1 + HAWK

- **왜**: 서비스에서 지연과 메모리를 줄일 수 있는지 보려고. HAWK는 학습 없이 시각 토큰만 줄이는 방법이라 E1에서 하나만 바꿔 비교할 수 있음. 원본 코드를 그대로 써서 우리 장비 · 과제에 그대로 옮겼을 때의 결과를 봄
- **해석**:
  - **Retention 20%로 Prefill −18%, E2E −18%, VRAM −0.66GB.** Prefill이 1/5로 줄지 않는 건 비전 인코더(약 0.9초)가 HAWK보다 앞에서 돌아 그대로이기 때문
  - **test Group6는 0.675 → 0.678로 그대로** → 결함 종류 판단에는 시각 토큰 20%로 충분. val에서는 0.657 → 0.617로 내려갔지만 100건이라 흔들림이 큼
  - **Grounding이 크게 무너짐** (Pointing 0.50 → 0.27, IoU@0.5 0.18 → 0.07). 버린 80% 토큰에 위치 정보가 있었다는 뜻. HAWK 논문은 질의응답만 평가해서 이 손실이 드러나지 않았던 것
  - 정리: 분류만 쓰면 쓸 만하지만, **박스까지 보여 주는 서비스에는 HAWK를 그대로 쓰기 어려움**

### E3-L — E1 + QLoRA (답의 앞머리만 학습)

- **왜**:
  - E1의 약점(Scope · Visibility, function · non_visual 놓침)은 출력 형식이 아니라 **판단 기준** 문제라 E0처럼 프롬프트로는 안 고쳐짐 → train 881로 기준을 직접 가르침
  - 16GB GPU라 4비트 모델은 얼려 두고 작은 LoRA 행렬만 학습 (QLoRA, 학습 변수 0.061%)
  - **앞머리(category · part · visibility)만 학습**: 13지표의 분류 지표가 모두 여기서 나오고, 근거 문장에는 정답 라벨이 없어서 학습할 수 없음. 앞머리만 바꾸면 박스 · 근거는 원래 모델 그대로라 E1과 깨끗하게 비교됨
  - 에폭 고르는 규칙을 학습 전에 정해 두고 val로만 고름 → test는 한 번만
- **해석**:
  - **E1의 약점이 사람 정답(test)에서도 고쳐짐**: Scope 0.376 → 0.656 (처음으로 R0 0.594를 넘음), Part 0.340 → 0.547, Visibility 0.507 → 0.720
  - **Group6 0.675 → 0.761 (+0.086)**. 그런데 val에서는 +0.173으로 두 배 → 학습 정답이 Claude가 단 silver라서, 같은 silver인 val에서는 Claude 라벨 방식을 따라 한 몫까지 점수에 들어감. 사람 정답 기준 실제 이득은 +0.09 정도 (185건으로는 "확실히 더 높다"와 "구분 안 됨"의 경계선)
  - **Grounding은 그대로** (Pointing 0.50 → 0.52, IoU@0.5 0.18 → 0.16) → 박스는 학습하지 않았으니 예상한 결과
  - **E2E 10.6 → 13.6초 (+29%)**, Prefill · VRAM은 거의 같음 → 어댑터를 모델에 합치지 않고 얹어 써서, 토큰 하나 만들 때마다 계산이 더 붙음. 합치면 없어지지만 4비트 모델이라 다시 양자화해야 해서 서비스 단계 과제로 남김
