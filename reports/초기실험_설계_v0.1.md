**실험 3개**

| 실험 | 내용 | 학습 | 검증 (val 100) | 평가 (test 185) |
|---|---|---|---|---|
| **E1 Qwen 제로샷** | Qwen2.5-VL-7B를 **공식 방식 그대로** + 우리 프롬프트 · 출력 형식 | 없음 | 돌림 → 문제 진단 | 1회 |
| **E2 + HAWK** | E1에 **HAWK 원본 코드**를 그대로 붙임 (시각 토큰 20%만 남김) | 없음 | 돌림 → E1과 짝 비교 | 1회 |
| **E3 문제 기반 개선** | E1 · E2에서 보인 문제에 맞춰 출력 형식 · 구조 변경 · LoRA 파인튜닝 등 | LoRA 등이면 train 881 | 설정 · 체크포인트 고르기 | 마지막 1회 |

실험 수에 안 세는 것: **E0 사전 점검** (dev, 정답 안 봄), **R0 참고선** (글만 보는 TF-IDF, 이미 돌림)

```
리뷰 글 + 사진(최대 4장) ─► [Qwen 공식 전처리] ─► Qwen2.5-VL-7B ─► JSON ─► 파싱·검증 ─► 분석 카드 ─► 평가 13지표
                                  │                  ▲
                    프롬프트 vlm-v0.3.3(E0 후)  E2: HAWK 원본 코드가 LLM 0층에서 시각 토큰을 20%만 남김
```

**원칙 4개**
1. **공식 그대로**: Qwen 모델 카드 · README의 추론 방식과 HAWK 저장소 코드를 고치지 않고 씀. 어쩔 수 없이 바꾼 곳은 1.2절과 E2 표에 이유와 함께 전부 적음
2. **test는 평가에만**, 설정마다 한 번. 무엇을 바꿀지는 val과 정답 없는 신호로만 정함. 단, 프롬프트의 뿌리는 라벨링 때 test를 보고 다듬은 것이라 **test가 프롬프트에 완전히 처음 보는 데이터는 아님** (3.4절) → test 122와 test_blind를 따로도 보고함
3. 한 번에 **하나만** 바꿈 (E1 → E2는 HAWK만, E3 변형마다 하나씩). 평가 코드가 두 실행의 설정 파일을 비교해 "깨끗한 짝"인지 확인함
4. 설정 파일(`_config.json`)이 없는 결과는 인정하지 않음. 설정이 다른데 같은 파일에 이어 쓰려 하면 코드가 멈춤

## 1. 백본과 추론 방식

### 1.1 공식 그대로 쓰는 것

| 항목 | 값 | 출처 |
|---|---|---|
| 모델 | `Qwen/Qwen2.5-VL-7B-Instruct` (HF 공식 가중치) | 팀 결정 |
| 로딩 | `Qwen2_5_VLForConditionalGeneration.from_pretrained(torch_dtype="auto", device_map="auto")` | 모델 카드 quickstart |
| 사진 처리 | `qwen_vl_utils.process_vision_info` → `processor(text, images)` | 모델 카드 |
| 해상도 | 사진당 **256~1,280 시각 토큰** (`min_pixels = 256×28×28`, `max_pixels = 1280×28×28`) | 모델 카드에 적힌 예시값 그대로 |
| 사진 번호 | `apply_chat_template(..., add_vision_id=True)` → 사진 앞에 "Picture 1: ", "Picture 2: " | README의 "Add vision ids" |
| 시스템 프롬프트 | 템플릿 기본값 "You are a helpful assistant." | chat_template.json |
| 디코딩 | greedy (`do_sample=False`). 나머지는 모델에 딸린 `generation_config.json` 그대로 (`repetition_penalty 1.05`) | HAWK `infer.py`와 같음. 원래 설정(온도 0.000001 샘플링)도 사실상 greedy |
| 어텐션 | sdpa | HAWK `infer.py`와 같음 (flash-attn은 Windows에서 못 씀) |
| 실행 환경 | **transformers 4.52.0** (HAWK가 검증하고 패치한 버전). E1 · E2 · E3를 모두 이 환경에서 돌림 | HAWK README · `setup_runtime.sh` |

- 실행은 `python -m cluvi.run_hawk ...`. HAWK의 `run.sh`가 bash로 하는 일(패치 확인 → HAWK `src`와 `.runtime/python`을 import 경로 앞에 둠)을 파이썬으로 똑같이 함. `run.sh`는 경로를 `:`로 이어서 Windows 파이썬과 우리 폴더 이름(공백 · 한글)에서 조용히 무시될 수 있어서
- 코드가 VLM 실행 때 **transformers 4.52.0이 `.runtime`에서 왔는지 확인하고, 아니면 멈춤**

### 1.2 어쩔 수 없이 바꾼 것 (이유)

| 바꾼 것 | 이유 |
|---|---|
| **LLM만 4비트 (NF4), 비전 인코더는 bf16** | 7B를 bf16으로 올리면 가중치만 16.6GB라 16GB GPU에 안 들어감. Qwen이 직접 낸 4비트판(AWQ)도 **비전 인코더는 양자화하지 않음** (`modules_to_not_convert: ["visual"]`) → 같은 나눔을 따름. AWQ판 자체는 `autoawq`가 transformers를 4.47로 내려 Qwen2.5-VL과 HAWK가 요구하는 버전과 충돌해서 못 씀. Qwen 공식 표에서 AWQ는 bf16보다 MMMU −2.8, MathVista −3.2, DocVQA −0.3 |
| 사진 EXIF 회전 | `qwen_vl_utils`는 회전 정보를 적용하지 않는데, 정답 박스는 세운 사진 기준. 세운 PIL 사진을 넘김 (PIL 입력은 공식 지원) |
| 사진 최대 4장 | test 185건 중 180건이 4장 이하. 넘으면 앞 4장 |
| `max_new_tokens = 640` | 카드 예시는 128. 근거 문장(한국어)이 있어 출력이 김 (실측 중앙값 214토큰) |
| 비용 측정 장치 | 매 단계 로짓 뒤에 붙는 기록기 하나: 첫 호출 시각 = prefill 끝, 고른 토큰 확률 1개만 저장. ViT 앞뒤 시계(hook). **계산 결과는 바꾸지 않음**. 확률표 전체를 쌓는 `output_scores`는 Peak VRAM을 부풀려서 뺌 (검수 지적) |

- 공식 설정이지만 문제가 됐던 것: `repetition_penalty 1.05`는 **프롬프트에 이미 나온 토큰에도** 적용됨 → v0.2에서 라벨 코드를 비튼 값("localizable")이 나옴. 프롬프트를 고친 v0.3.3에서는 1.05로도 형식이 맞아서 **공식값 그대로 씀** (6절 E0)
- test 185 기준 시각 토큰: 리뷰당 평균 2,082개, 중앙값 1,271, 상위 10% 3,690, 최대 4,988. min_pixels 때문에 커지는 사진은 0장
- 거절한 대안: bf16 + CPU 분산 (지연 측정이 의미 없어짐), 8비트 (bf16에 더 가깝지만 디코딩이 훨씬 느려 비용 비교가 왜곡됨)

- 프롬프트 글 (3절)
- 출력 JSON 형식과 그 파싱 (2절)

## 2. 출력 형식

### 2.1 최종 분석 카드 (에이전트와 평가가 받는 것)

```json
{
  "part_scope": "product",
  "part": "sleeve",
  "group6": "damage",
  "group5": "physical_defect",
  "defect": "tear_hole",
  "visibility": "localized",
  "boxes": [
    {"image_index": 0, "bbox": [0.35, 0.20, 0.60, 0.55], "target": "defect"}
  ],
  "evidence": {
    "customer_claim": "고객은 소매가 찢어진 상태로 배송되었다고 주장함",
    "review_span": "The sleeve arrived torn.",
    "visual_findings": [
      {"image_index": 0, "description": "소매 봉제선 근처에 찢어진 부분이 보임", "box_ref": 0}
    ],
    "claim_support": "supported",
    "limitations": ["손상이 발생한 시점과 원인은 확인할 수 없음"]
  },
  "valid": true,
  "issues": [],
  "conf": {"group6": 0.93},
  "cost": {"visual_tokens": 1272, "visual_tokens_full": 1272, "prefill_ms": 0, "e2e_ms": 0, "peak_vram_gb": 0}
}
```

팀 안의 JSON에 아래 넷을 더함: `group5` (지표에 필요), `valid` · `issues` (형식 검사), `conf` (cascade용 확신도, 기록만), `cost` (비용 지표).

### 2.2 모델이 직접 쓰는 것 vs 코드가 만드는 것

| 필드 | 누가 | 방법 |
|---|---|---|
| part, group6, defect, visibility | 모델 | 목록 안의 코드로 답함 |
| `part_scope` | **코드** | part 코드표에서 자동 (`sleeve` → `product`) |
| `group5` | **코드** | damage · manufacturing → `physical_defect`, 나머지는 group6 그대로 |
| boxes | 모델 → 코드 | 모델은 Qwen 공식 형식 `{"bbox_2d": [x1,y1,x2,y2], "label": …}`으로, **자기가 본(리사이즈된) 사진의 픽셀 좌표**로 답함 (기술보고서 2.1.2절, 공식 grounding 예제가 `image_grid_thw × 14`로 나눔). 사진은 `"picture": 1, 2, …`. 코드가 0~1 `bbox`와 0부터 세는 `image_index`로 바꿈. 사진 크기를 벗어난 좌표는 `box_out_of_range`로 표시 |
| evidence 5칸 | 모델 | 한국어 3칸 (customer_claim, description, limitations), 영어 원문 1칸 (review_span), 선택지 1칸 (claim_support). `box_ref`도 1부터 셈 → 코드가 바꿈 |
| valid, issues, conf, cost | 코드 | 파싱 · 측정 결과 |

### 2.3 필드 설명

**① 부위 (Part)** — "문제가 보이는 곳"이 아니라 **"문제가 실제로 있는 곳"**

| part_scope | part (도메인별) |
|---|---|
| product | Books: cover, corner, spine_binding, pages, print_surface · Fashion: body_fabric, seam, pocket, sleeve, collar, fastener, print_deco, lining, hem · Electronics: housing, display, camera, battery, port, button, audio, internal, software · Edible: contents, container · 모든 도메인: whole |
| packaging | outer_box, product_package, seal |
| accessory | charger_cable, other_accessory |
| label_doc | label, manual |
| none | none (서비스 · 가격 불만) |
| other | other (목록에 없는 부위) |

**② 결함 대분류 group6와 세부 결함 defect**

| group6 | 뜻 | defect (세부 27종) |
|---|---|---|
| `damage` 파손 | 찢어짐 · 깨짐 · 눌림 · 긁힘 · 개봉 흔적 (받았을 때) | tear_hole, crush_break, scratch, opened_tampered |
| `contamination` 오염 | 벌레 · 곰팡이 · 이물질 · 얼룩 | pest, mold_spoil, foreign_object, stain_dirt |
| `manufacturing` 제조 불량 | 처음부터 잘못 만듦: 얇은 소재, 봉제, 인쇄, 색, 화면, 조립 | material, stitching, print, color, display, assembly |
| `not_as_described` 설명과 다름 | **주문 · 광고와 다른 물건**: 가짜, 다른 제품 · 사이즈 · 색, 빠진 구성품, 중고, 유통기한 | counterfeit_wrong, missing, used, label_expiry |
| `function` 기능 | 멀쩡해 보이는데 안 되거나 잘 안 됨, 안 맞음, 불편한 설계 | malfunction, performance, fit_size, design_usability |
| `non_visual` 사진과 무관 | 맛 · 냄새, 배송 · 환불 · 서비스, 가격, 책 내용, 구체적 불만 없음 | taste_smell, content, service, price, vague |

- group5 = group6에서 damage + manufacturing을 `physical_defect`로 합친 5분류. 사람끼리도 가장 헷갈리는 경계라서 따로 봄
- defect가 고른 group 아래 목록에 없으면 defect만 비우고 group은 살림 (`issues`에 `defect_not_in_group`)

**③ 보임 정도 (Visibility)와 박스**

| visibility | 뜻 | 박스 |
|---|---|---|
| localized | 사진 특정 위치에 결함(또는 증거: 에러 화면, 지난 날짜, 깨진 화면)이 보임 | 1~3개, 가장 잘 보이는 것 먼저 |
| diffuse | 보이지만 제품 전체에 퍼짐 (색, 핏, 전체적으로 얇음, 확연히 다른 가짜) | 없음 |
| not_visible | 사진으로 안 보임 (기능, 맛, 서비스, 빠진 구성품, 무관한 사진) | 없음 |

박스 `target`: `defect` = 결함 자체 (구멍, 벌레, 번진 인쇄) / `evidence` = 문제를 증명하는 표시 (경고 화면, 날짜). 사이즈 태그 · 가격표는 증거가 아님.

**④ 근거 (Evidence)** — 상담원 화면에 그대로 보여줄 설명. **고객 말과 사진에서 본 것을 섞지 않는 것**이 핵심

| 칸 | 내용 | 규칙 |
|---|---|---|
| `customer_claim` | 고객이 무엇을 문제 삼는지 (한국어 1문장) | "고객은 …라고 주장함" 형태. 시점 · 원인 주장도 남기되 **사실처럼 쓰지 않음** |
| `review_span` | 그 주장이 나온 리뷰 원문 (영어, 20단어 이하) | **한 글자도 바꾸지 않고 복사**. 코드가 원문에 있는지 검사 (`review_span_not_verbatim`) |
| `visual_findings` | 사진마다 실제로 보이는 것 (한국어) | 위치 · 모양 · 색만. 관련 없는 사진은 그렇다고 씀. `box_ref` = 맞는 박스 번호 |
| `claim_support` | 사진이 고객 주장을 받쳐 주는가 | `supported` / `partially_supported` / `not_verifiable` (**사진으로 확인 불가, 거짓이라는 뜻 아님**) / `contradicted` |
| `limitations` | 사진으로 확인할 수 없는 것 (한국어 0~2개) | 언제 · 어떻게 생겼는지, 누구 탓인지, 작동 여부, 맛. **원인을 추측하지 않음** |

### 2.4 정답이 없는 칸을 어떻게 보나

`evidence`에는 정답 라벨이 없음. 그래서 **헤드라인 지표에 넣지 않고** 아래 세 가지로만 봄.

| 방법 | 무엇 | 비용 |
|---|---|---|
| 자동 검사 | review_span 원문 일치율, box_ref가 실제 박스를 가리키는가, 칸이 비었는가 | 0 (평가 코드 `--format`) |
| 일관성 표 | 예측 visibility × claim_support 교차표. not_visible인데 supported가 많으면 이상 | 0 (`--format`) |
| 사람 점검 | test에서 30건을 뽑아 한국어 근거만 읽고 "사진과 맞나 / 고객 말을 사실처럼 썼나" 예 · 아니오 | 약 20분 |

## 3. 프롬프트 `vlm-v0.2` → E0에서 고친 `vlm-v0.3.1`

- 원문 파일: `cluvi/prompts/<버전>.txt` (코드가 이 파일을 읽음. 버전 = 파일 이름)

## 4. 평가지표 13개 — 정의

용어: **Macro-F1** = 클래스마다 F1을 따로 구해 단순 평균 (작은 클래스도 같은 비중). **IoU** = 두 박스가 겹친 넓이 ÷ 합친 넓이.

| 항목 | 지표 | 정의 | test 185 중 채점 건수 |
|---|---|---|---|
| Part | **Scope Macro-F1** | part_scope의 Macro-F1 (6종 중 test에 나온 5종. label_doc은 0건) | 122 |
| Part | **Part Macro-F1** | part 코드의 Macro-F1 (도메인 섞어서, test에 나온 24종) | 122 |
| Defect | **Group6 Macro-F1** ★주 지표 | 6개 그룹의 Macro-F1 + bootstrap 95% 신뢰구간. test 122 · test_blind 따로도 | 176 |
| Defect | **Group5 Macro-F1** | 5개 그룹의 Macro-F1 | 176 |
| Defect | **Fine-grained Macro-F1** | 세부 결함의 Macro-F1 (test에 나온 24종) | 122 |
| Visibility | **Macro-F1** | 3단계의 Macro-F1. test 122 · test_blind 따로도 | 176 |
| Grounding | **Mean IoU** | 아래 "박스 채점" 참고 | 56 (정답이 localized이고 박스 있음) |
| Grounding | **IoU@0.5** | IoU ≥ 0.5인 비율 | 56 |
| Grounding | **Pointing Accuracy** | 예측 박스 **중심점**이 같은 사진의 정답 박스 안에 있는 비율 | 56 |
| Token | **Retention Ratio (%)** | LLM에 들어간 시각 토큰 합 ÷ 기준(E1 설정) 시각 토큰 합 × 100. E2는 HAWK가 알려 주는 "남긴 시각 토큰 수"로 셈 | 185 |
| Efficiency | **Prefill Latency (ms)** | 입력이 GPU에 올라간 뒤 **첫 출력 토큰이 나올 때까지** (ViT 포함). 중앙값 + p90 | 185 |
| Efficiency | **End-to-End Latency (ms)** | 사진 파일 열기부터 마지막 토큰까지 (전처리 + prefill + 디코딩). 중앙값 + p90 | 185 |
| Efficiency | **Peak VRAM (GB)** | 리뷰마다 `torch.cuda.max_memory_allocated`, 실행 전체의 최댓값 | 185 |

val 100에서도 같은 13지표를 냄 (정답은 silver). 숫자 표에는 val Group6 F1을 옆에 같이 적음.

**채점 규칙**
- Macro-F1은 **정답에 나온 클래스만** 평균. 목록 밖 값이나 빈칸은 `INVALID` = 오답. 칸마다 따로 채점
- **박스 채점**: 모델의 **첫 번째 박스**를 **같은 사진**의 정답 박스들과 비교해 가장 큰 IoU. 박스가 없거나 다른 사진이면 IoU 0, 실패. 56건뿐이라 거칠게만 읽음 (1건 = 1.8%p)
- 예측이 빠진 리뷰가 있으면 평가 코드가 `!!`로 크게 알림
- 비용 측정: batch 1, 같은 GPU, 다른 GPU 작업 없이, warm-up 2건 제외. 이 GPU는 화면 출력도 같이 함 → 측정 중에는 다른 프로그램을 띄우지 않음

**비교와 통계**
- 두 실행 비교는 **같은 리뷰끼리 짝지은 bootstrap** (2,000회) 95% 신뢰구간
- 신뢰구간이 0을 포함하면 "차이 없음"이 아니라 **"이 표본 크기로는 구분 안 됨"**으로 적음. test 176건에서 짝지은 신뢰구간은 대략 ±0.05~0.07로 예상
- **답 바뀜 비율 (flip rate)**: 같은 리뷰에서 group6 예측이 두 실행 사이에 바뀐 비율. 정답이 필요 없어서 val · test 모두에서 냄
- **E2 (HAWK) 판정 기준 (안, 미리 정함)**: 짝지은 차이 신뢰구간 하한 ≥ **−0.05** (Group6 Macro-F1)이면 "−5%p 범위 안에서 떨어지지 않음". HAWK 논문식 **상대 성능**(E1 = 100%)과 답 바뀜 비율도 같이 적음. −0.05는 팀 확정 필요

**함께 보는 보조 지표**: group6 정확도, JSON 정상 출력률(valid), 형식 문제 종류(issues), 출력 토큰 수, 단계별 시간(vision / decode), 잘린 출력 수, VRAM 한계 근접 표시, 근거 자동 검사
