# E1·E2 코드로 따라가기: 리뷰 한 건이 상담원 카드가 되기까지

6팀 CluVi · CESAMARD · 공부 노트 (2026-11-15)

> **GitHub에서 볼 때**: `HAWK/` · `.venv/` 아래를 가리키는 링크는 로컬에만 있는 파일이라 레포에서는 열리지 않습니다. 로컬 파일은 HAWK 클론, HAWK가 패치한 transformers 4.52.0 런타임, 설치된 패키지입니다. HAWK 원본 코드는 https://github.com/peppery77/HAWK/tree/3af2071 에서 볼 수 있습니다. 설치 패키지는 transformers · PEFT 저장소의 같은 버전 태그에서 볼 수 있습니다. 결과 페이지 `reports/Qwen_베이스라인_실험결과.html`은 고객 사진이 들어 있어 레포에 올리지 않았습니다.

이 노트는 이미 끝난 두 실험을 **코드 줄 단위로** 따라갑니다.

- **E1**: Qwen2.5-VL-7B 제로샷. 공식 추론 방식에 우리 프롬프트와 출력 형식만 얹었습니다.
- **E2**: E1에 HAWK 원본 코드를 켜서 시각 토큰을 20%만 남겼습니다.

리뷰 한 건이 지나가는 순서대로 다섯 단계로 나눴습니다. 단계마다 세 가지를 같이 봅니다.

1. 그 자리의 **코드**: 링크를 누르면 해당 줄로 갑니다.
2. 그 코드가 해당하는 **논문 위치**
3. 그 코드에서 나온 **우리 실험 숫자**와 **상담원 카드에서 하는 일**


### 1-6. 사진 크기 맞추기: `smart_resize` [Qwen]

**[models.py:58](../../../cluvi/models.py#L58)** → **[vision_process.py:468](../../../HAWK/.runtime/python/qwen_vl_utils/vision_process.py#L468) `process_vision_info`** → **[vision_process.py:98](../../../HAWK/.runtime/python/qwen_vl_utils/vision_process.py#L98) `fetch_image`**

- [135-136줄](../../../HAWK/.runtime/python/qwen_vl_utils/vision_process.py#L135): 사진마다 넘긴 `min_pixels`·`max_pixels`를 읽습니다.
  - 우리 값은 [models.py:25-26](../../../cluvi/models.py#L25): 256×28×28 ~ 1280×28×28 = 사진당 256~1,280토큰.
  - 기본값은 [vision_process.py:27-28](../../../HAWK/.runtime/python/qwen_vl_utils/vision_process.py#L27): 4~16,384토큰.
- [144줄](../../../HAWK/.runtime/python/qwen_vl_utils/vision_process.py#L144): `image.resize(...)`로 실제로 줄입니다.

**[vision_process.py:60-86](../../../HAWK/.runtime/python/qwen_vl_utils/vision_process.py#L60) `smart_resize`**: 직접 손으로 계산해 봅니다 (4,000×3,000 사진).

```
① 76-77줄: 가로·세로를 28의 배수로 반올림
   세로 3000/28 = 107.1 → 107×28 = 2,996
   가로 4000/28 = 142.9 → 143×28 = 4,004
② 78줄: 2,996 × 4,004 = 1,200만 px > max_pixels 1,003,520 → 줄여야 함
③ 79줄: beta = √(3000×4000 / 1,003,520) = √11.96 = 3.458   (가로·세로를 같은 비율로 나눌 값)
④ 80-81줄: 28의 배수로 내림
   세로 3000/3.458 = 867.5 → 867.5/28 = 30.98 → 30×28 =   840
   가로 4000/3.458 = 1156.7 → 1156.7/28 = 41.3  → 41×28 = 1,148
⑤ 결과: 1,148 × 840 = 964,320 px (상한 안), 비율 1.367 (원본 1.333과 거의 같음)
```

| 원본 (가로×세로) | 모델이 보는 크기 | 시각 토큰 (우리 설정) | 기본 설정이었다면 |
|---|---|---|---|
| 4,000 × 3,000 | 1,148 × 840 | 41 × 30 = **1,230** | 15,301 |
| 1,080 × 1,920 | 728 × 1,316 | 1,222 | 2,691 |
| 500 × 500 | 504 × 504 | 324 | 324 |

> **우리 코드에도 같은 계산이 있습니다.** [models.py:36](../../../cluvi/models.py#L36) `seen_sizes`는 transformers 쪽 `smart_resize`를 불러 같은 크기를 미리 계산합니다. [models.py:42](../../../cluvi/models.py#L42) `visual_tokens_at`는 (w÷28)×(h÷28)로 토큰 수를 셉니다. [models.py:249-251](../../../cluvi/models.py#L249)는 "미리 센 값 = 실제 토큰 수"인지 매번 공짜로 확인합니다. test 185건 모두 같았습니다.

## 3단계. LLM이 답 쓰기

> 한 줄 요약: 글 임베딩과 사진 토큰을 한 줄로 이어, 각 토큰에 (시간, 세로, 가로) 위치 번호를 붙입니다. 4bit로 줄인 28층 LLM이 이것을 한 번에 읽고(prefill), 그 뒤로는 확률이 가장 높은 토큰을 하나씩 약 220번 뽑습니다(디코딩).

### 3-1. 위치 번호: M-RoPE

**[modeling:1698-1712](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1698)**: prefill 때 한 번만 `get_rope_index`를 부릅니다.

**[modeling:1405-1565](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1405) `get_rope_index`**

- [1533-1536줄](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1533): 사진 앞 글 토큰은 세 축(t, h, w)에 **같은 번호** 0, 1, 2, ...를 줍니다. 보통 LLM의 1D 위치와 같습니다.
- [1546-1553줄](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1546): 사진 토큰 번호입니다.
  - t는 사진 안에서 모두 같고, h는 병합 격자의 행 번호, w는 열 번호입니다.
  - 여기에 앞 글의 끝 번호를 더합니다.
- [1556-1559줄](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1556): 사진 뒤 글은 **사진 번호들 가운데 가장 큰 값 + 1**부터 다시 셉니다.

우리 예시로 계산해 봅니다. 사진 앞 템플릿은 20토큰이고, 병합 격자는 세로 30 × 가로 41입니다.

```
토큰 위치(순서)    0 ... 19 │ 20 ............................. 1249 │ 1250 1251 ...
                 글 20개    │ 사진 토큰 1,230개                       │ <ve> 프롬프트 ...
  t (시간)       0 ... 19   │ 20 20 20 ...                  20       │ 61   62  ...
  h (세로)       0 ... 19   │ 20 20 ... (행 0)  ...  49 (행 29)      │ 61   62  ...
  w (가로)       0 ... 19   │ 20 21 ... 60 (열 0~40) 반복           │ 61   62  ...
```

- 사진 하나가 **토큰 1,230칸을 차지하지만 위치 번호는 41칸만** 앞으로 갑니다.
- [1563줄](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1563): 그래서 `rope_deltas` = (가장 큰 번호 + 1) − (토큰 수)는 음수가 됩니다. 이 예시에서는 −1,189입니다.
- [1714-1726줄](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1714): 디코딩 때 새 토큰의 위치 = `cache_position + rope_deltas`
  - **5단계에서 HAWK가 이 값을 고쳐야 하는 이유**가 여기 있습니다.

**위치 번호를 q·k에 적용하는 곳**

- [modeling:627](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L627) `apply_multimodal_rotary_pos_emb`의 [659-665줄](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L659)
- 설정 `"mrope_section": [16, 24, 24]`
  - 헤드 하나는 128차원이고, 회전 주파수는 64쌍입니다.
  - 64쌍 가운데 16쌍은 t 번호로, 24쌍은 h 번호로, 24쌍은 w 번호로 돌립니다.
- 2단계 2D RoPE(ViT 안)와 같은 생각을 LLM으로 넓힌 것입니다.

**논문**: Qwen2.5-VL 2.1.3. 글은 세 축이 같은 번호라 1D RoPE와 같고, 사진은 t가 일정하고 h·w가 공간 위치를 따른다는 설명입니다. 사진 뒤 글이 "가장 큰 값 + 1"부터 이어진다는 건 논문에 없고 코드에만 있습니다.

> **박스와의 연결**: 모델은 시각 토큰마다 (h, w) 번호를 알기 때문에 "이 토큰은 사진의 몇째 줄 몇째 칸"을 압니다. 그래서 박스를 **픽셀 좌표**로 답할 수 있습니다. 논문 2.1.2는 좌표를 0~1로 정규화하지 않고 입력 사진의 실제 크기로 박스를 나타낸다고 말합니다. 2.2.1의 grounding 학습 데이터도 같은 방식입니다.

### 3-3. `generate`: prefill 한 번, 디코딩 약 220번

**[models.py:190-192](../../../cluvi/models.py#L190)**

```python
seq = self.model.generate(**enc, max_new_tokens=640, do_sample=False,
                          logits_processor=LogitsProcessorList([StepRecorder()]), **self.gen_override)
```

- `do_sample=False` = **greedy**입니다. 매번 확률이 가장 높은 토큰을 고릅니다.
  - 같은 입력이면 같은 카드가 나옵니다. 재현이 됩니다.
- 따로 넘기지 않은 값은 HF 캐시의 `generation_config.json`을 그대로 씁니다.

```json
{"do_sample": true, "temperature": 0.000001, "repetition_penalty": 1.05, "eos_token_id": [151645, 151643]}
```

- `temperature 1e-6` 샘플링은 사실상 greedy라서, `do_sample=False`로 둔 것과 결과가 같습니다.
- `repetition_penalty 1.05`는 **이미 나온 모든 토큰(프롬프트 포함)**의 점수를 깎습니다.
  - E0에서 v0.2 프롬프트가 라벨 코드를 피하다가 `localizable` 같은 말을 지어낸 원인이었습니다.
  - v0.3.3 출력 틀에서는 1.05로도 형식이 맞아서 공식값을 그대로 썼습니다.
- `eos_token_id`의 151645는 `<|im_end|>`입니다. 이게 나오면 멈춥니다.

**prefill과 디코딩**

```
prefill  : [토큰 3,105개] ──► ViT + LLM 28층 한 번 ──► 첫 출력 토큰 '{'
           (이때 KV 캐시 3,105칸이 쌓임)
decode   : '{' ──► 28층 (새 토큰 1개만, KV 캐시 3,105칸을 봄) ──► '"'
           '"' ──► 28층 (KV 3,106칸) ──► 'category'
           ... 약 220번 ... ──► <|im_end|> 멈춤
```

- [modeling:2017-2019](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L2017): 디코딩 단계에서는 `pixel_values=None`입니다. ViT는 prefill 때 한 번만 돕니다.
- **시간 재기** [models.py:175-184](../../../cluvi/models.py#L175) `StepRecorder`
  - 매 단계 logits가 나온 직후에 불립니다.
  - **첫 호출 시각 = prefill 끝**입니다.
  - 고른 토큰의 확률만 저장합니다. 전체 점수표(`output_scores`)를 쌓으면 VRAM이 부풀기 때문입니다.
- [models.py:201-211](../../../cluvi/models.py#L201): 시간과 메모리 기록입니다.
  - `prefill_ms` = 입력이 GPU에 올라간 뒤부터 첫 토큰까지 (ViT 포함)
  - `decode_ms` = 나머지
  - `e2e_ms` = 사진 파일 열기부터 마지막 토큰까지
  - `peak_vram_gb` = `max_memory_allocated`
- [models.py:195-197](../../../cluvi/models.py#L195): **뽑은 토큰만** 잘라 글로 바꿉니다.
  - 앞에서부터 프롬프트 길이만큼 자르지 않고, 뒤에서부터 "뽑은 개수"만큼 자릅니다.
  - HAWK가 프롬프트 길이를 줄이기 때문입니다 (5단계).

## 5단계. HAWK가 끼어드는 길 (E2)

> 한 줄 요약: ViT가 다 돈 뒤, LLM에 넣기 직전에 끼어듭니다. LLM 0층의 q·k 투영만 미리 한 번 계산해, 프롬프트 토큰들이 각 사진 토큰을 얼마나 쳐다보는지 잽니다. 이 점수에 헤드별 고정 가중치 28개를 곱해 합하고, 상위 20%만 남깁니다. 남은 토큰은 **원래 위치 번호를 그대로** 가지고 LLM 28층 전부를 지나갑니다.

**[pruning.py:190-332](../../../HAWK/src/hawk/pruning.py#L190)**

**① 사진 토큰 위치 찾기**: [212-216줄](../../../HAWK/src/hawk/pruning.py#L212)

  - 사진 사이의 `"Picture 2: "` 같은 글은 마지막 사진 앞이라 질문에 안 들어갑니다.

```
<sys> ... Picture 1: <vs>■■■■<ve>Picture 2: <vs>■■■■<ve>Amazon India ... 출력 틀 }<|im_end|> <|im_start|>assistant
                                                     └──────── 질문 T (1,542토큰) ────────┘
                     └─ 사진 토큰 V (모든 사진 합쳐서) ─┘
```

**③ LLM 0층의 q·k만 미리 계산**: [259-272줄](../../../HAWK/src/hawk/pruning.py#L259)
- [261줄](../../../HAWK/src/hawk/pruning.py#L261): 0층의 `input_layernorm`을 적용합니다.
- [268-269줄](../../../HAWK/src/hawk/pruning.py#L268): 0층 `q_proj`·`k_proj`를 **전체 시퀀스(3,105토큰)**에 적용합니다.
  - 우리 실행에서 이 두 층은 **NF4 4bit**입니다.
  - 헤드 가중치는 bf16 모델에서 구한 값이라, 점수가 원본과 조금 다를 수 있습니다.
- **RoPE 회전을 하지 않은** q·k입니다. 논문도 위치 편향을 피하려고 RoPE를 뺐다고 적었습니다.
- [272줄](../../../HAWK/src/hawk/pruning.py#L272): k 4헤드를 28헤드로 복사합니다 (3-2의 GQA).
- [274-275줄](../../../HAWK/src/hawk/pruning.py#L274): q는 질문 T의 줄만, k는 사진 V의 줄만 골라냅니다.

**④ 점수 계산**: [67-127줄](../../../HAWK/src/hawk/pruning.py#L67) `compute_hawk_scores`

```
[96-97줄]   A_h = Q_h · K_hᵀ / √128           헤드 h마다 (T × V) 행렬. softmax 없음
[98줄]      c_h = A_h를 T 방향으로 평균        → 길이 V: "질문 전체가 사진 토큰 j를 평균 얼마나 보나"
[103-104줄] c_h = c_h / ‖c_h‖₂                 헤드마다 L2 정규화 (헤드 간 크기 차이 없앰)
[126-127줄] 점수_j = Σ_h w_h · c_h,j           헤드 중요도 28개로 가중합
```

- 논문(3.3절)의 식 4~7과 대응합니다.
  - 식 4: 0층 Q·K, 식 5: QKᵀ/√d, 식 6: 질문 토큰 평균, 식 7: 헤드 가중합
- **차이 하나**: 논문 식에는 헤드마다 L2로 나누는 단계가 없고, 코드에는 있습니다 ([103-104줄](../../../HAWK/src/hawk/pruning.py#L103), 설정 `"l2"`).
- 계산 크기: 28헤드 × 1,542 × 1,271 ≈ 5,500만 칸. 잠깐 쓰고 버립니다.

**⑤ 상위 20% 고르기**: [130-155줄](../../../HAWK/src/hawk/pruning.py#L130) `select_keep_indices`
- [147줄](../../../HAWK/src/hawk/pruning.py#L147): `keep = ceil(V × 0.20)`
  - 예시 1,230 → **246**, test 중앙 1,271 → 255. 실제 비율은 0.200~0.201입니다.
- [149줄](../../../HAWK/src/hawk/pruning.py#L149): `topk`를 **모든 사진을 한데 모은 점수**에서 고릅니다.
  - 사진마다 몫을 보장하지 않습니다. 한 장이 몫을 거의 다 가져갈 수 있습니다.
- [150줄](../../../HAWK/src/hawk/pruning.py#L150): 고른 토큰을 원래 순서대로 정렬합니다.
- [152-155줄](../../../HAWK/src/hawk/pruning.py#L152): 글 토큰은 전부 남기고, 사진 토큰은 고른 것만 남기는 마스크를 만듭니다.

**⑥ 텐서 잘라 내기**: [310-331줄](../../../HAWK/src/hawk/pruning.py#L310)
- `inputs_embeds`, `attention_mask`, `position_ids`를 같은 `keep_indices`로 `index_select`합니다.
- [315-319줄](../../../HAWK/src/hawk/pruning.py#L315): **위치 번호도 같이 골라 냅니다.**
  - 남은 사진 토큰은 원래 (t, h, w) 번호를 그대로 가집니다.
  - 격자에 구멍이 숭숭 나지만, 남은 토큰이 사진의 어디였는지는 모델이 압니다.
- [320-322줄](../../../HAWK/src/hawk/pruning.py#L320): `cache_position`은 0~(남은 길이−1)로 줄입니다. KV 캐시의 칸 번호이기 때문입니다.

```
E1:  [글 20][사진 1,230][글 1,855]  = 3,105토큰 → 28층
E2:  [글 20][사진  246][글 1,855]  = 2,121토큰 → 28층   (예시 사진 1장 기준)
            ↑ 남은 246개는 원래 h·w 번호를 그대로 가짐 (빈자리는 번호만 비어 있음)
```

> **바로잡기**: HAWK 해설 페이지에는 "나머지 27층은 짧아진 시퀀스로 돈다"고 적혀 있습니다. 코드로 보면 0층의 q·k **투영만** 전체 길이로 한 번 더 계산하고, 그다음 **0층을 포함한 28층 전부**가 짧아진 시퀀스로 돕니다 ([1762줄](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1762)).

### 5-6. E2 숫자를 코드로 풀기

**① 시각 토큰 1,271 → 255 (20.0%)**
- [pruning.py:147](../../../HAWK/src/hawk/pruning.py#L147)의 `ceil(V × 0.20)` 그대로입니다.

**② Prefill −18% (2.05 → 1.69초): 토큰을 80% 버렸는데 왜 18%뿐인가**
- LLM에 들어가는 토큰은 3,105 → 약 2,089로 **33%만** 줄었습니다.
  - 프롬프트 1,542토큰과 템플릿은 그대로 남기 때문입니다.
- ViT 0.88초는 그대로입니다 (2단계 정리).
- LLM 부분만 보면 약 1.17 → 약 0.80초(−32%)로, 토큰이 줄어든 비율과 거의 같습니다.
- 그래서 전체 prefill은 −18%입니다.
- 거기에 HAWK가 0층 q·k를 전체 길이로 한 번 더 계산하는 비용이 조금 붙습니다 (5-3 ③).

**③ 디코딩 −11% (7.14 → 6.33초)**
- 새 토큰 하나를 만들 때마다 KV 캐시 전체를 봅니다.
- 캐시가 3,105칸 → 약 2,089칸으로 짧아져 한 걸음씩 조금 빨라졌습니다.
- E2E 절감 1.89초 가운데 0.82초가 디코딩에서 나왔습니다. **prefill에서 아낀 0.36초보다 큽니다.**

**④ VRAM −0.66GB (9.08 → 8.41GB)**: 코드로 추정한 몫입니다. 재 보지는 않았습니다.
- [modeling:1961](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1961): 이 버전은 prefill 때 **모든 위치의 logits**를 만듭니다.
  - 3,105 × 152,064 × 2바이트 ≈ 0.94GB → 2,089토큰이면 0.64GB. **약 0.3GB 차이로 가장 큰 몫**입니다.
- KV 캐시는 토큰당 28층 × 2(K·V) × 4헤드 × 128 × 2바이트 = 56KB입니다. 1,016토큰이면 약 0.06GB로 작습니다.
- 나머지는 prefill 중간 계산값(MLP 18,944차원 등)이 짧아진 몫입니다.

**⑤ 분류는 지킴 (Group6 0.675 → 0.678)**
- HAWK 논문 Table 3(원본 해상도, Qwen2.5-VL-7B, 80% 제거)은 벤치마크 10개 평균 원래 성능의 96.2%입니다.
- Table 1(고정 1008, 1,296 → 256)은 96.0%입니다.
- 우리 group6는 100.4%라서, 논문이 말하는 "20%만 남겨도 대부분 유지"와 맞습니다.

**⑥ 박스는 무너짐 (Pointing 0.50 → 0.27, mIoU 0.238 → 0.142)**
- **논문은 grounding·박스 과제를 평가하지 않았습니다.** 헤드 가중치도 일반 VQA 벤치마크로 구했습니다.
- 그래서 박스 하락은 논문이 시험한 범위 밖에서 나온 결과입니다.
- 코드에서 짚이는 원인 후보 넷입니다. 모두 가설이고, 검증하려면 GPU로 다시 돌려야 합니다.

**⑦ 논문 효율 표와 비교**
- HAWK 논문 Table 5(MME, A100, bf16, 80% 제거): 벤치마크 전체 E2E 20분 15초 → 15분 4초 = **×1.34 (74.4%로)**, 메모리 16.9 → 15.7GB
- 우리는 ×1.22(−18%)입니다.
- 차이가 나는 이유 셋:
  - MME는 답이 Yes/No처럼 짧아서 prefill 비중이 큽니다 (추론).
  - 우리 ViT는 sdpa 경로라 비전 몫이 큽니다.
  - 우리 질문 1,542토큰은 줄지 않습니다.
- 논문은 prefill만 따로 재지 않았습니다. 우리 prefill 정의는 VisionZip 3.3절을 따랐습니다.

## 7. 스스로 확인 문제

<details>
<summary>Q1. 1,600×1,200 사진은 시각 토큰 몇 개가 되나요? (우리 설정)</summary>

반올림: 1,596 × 1,204 → 192만 px > 상한 → beta = √(1,920,000 / 1,003,520) = 1.383 → 가로 1,600/1.383 = 1,156.7 → 41×28 = 1,148, 세로 1,200/1.383 = 867.5 → 30×28 = 840 → 41 × 30 = **1,230개**. 4,000×3,000과 비율이 같아서 결과도 같습니다.
</details>

<details>
<summary>Q2. 사진 2장을 올린 리뷰에서, ViT 안의 사진 1 조각이 사진 2 조각을 볼 수 있나요?</summary>

없습니다. full attention 층도 `cu_seqlens`가 사진마다 끊겨 있습니다 ([modeling:510-518](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L510)). 두 사진은 LLM에 들어가서야 서로 만납니다.
</details>

<details>
<summary>Q3. 사진 하나(병합 격자 30×41)는 시퀀스에서 몇 칸을 차지하고, 위치 번호는 몇 칸 앞으로 가나요?</summary>

1,230칸을 차지하고, 위치 번호는 max(30, 41) = **41칸**만 갑니다 ([modeling:1546-1559](../../../HAWK/.runtime/python/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py#L1546)). 그래서 `rope_deltas`가 음수입니다.
</details>

<details>
<summary>Q4. HAWK가 0.20을 남겼는데 prefill이 80%가 아니라 18%만 줄어든 이유 두 가지는?</summary>

(1) ViT 0.88초는 HAWK 앞에서 이미 다 돌았습니다. (2) LLM 입력 중 프롬프트 1,542토큰은 그대로라, LLM이 읽는 토큰은 33%만 줄었습니다.
</details>

<details>
<summary>Q5. HAWK가 `rope_deltas`를 안 고치면 무슨 일이 생기나요?</summary>

디코딩 위치 = `cache_position + rope_deltas`입니다. 지운 뒤 `cache_position`이 작게 시작하므로, 출력 토큰들이 원래보다 앞선 위치 번호를 받아 프롬프트 끝 위치와 겹칩니다. 그러면 출력이 망가질 수 있습니다 ([utils.py:3581-3584](../../../HAWK/.runtime/python/transformers/generation/utils.py#L3581)).
</details>

<details>
<summary>Q6. 모델이 박스를 [574, 420, 700, 560]으로 답했고 그 사진은 1,148×840으로 보였습니다. 카드에 들어가는 값은?</summary>

[574/1148, 420/840, 700/1148, 560/840] = **[0.5, 0.5, 0.6098, 0.6667]** ([common.py:292](../../../cluvi/common.py#L292)). 원본 4,000×3,000으로 나누면 틀립니다.
</details>

<details>
<summary>Q7. E2 − E1 = +0.004 [−0.048, +0.046]인데 왜 "더 좋다"가 아니라 "비열등"이라고 하나요?</summary>

구간이 0을 포함하므로 차이를 구분할 수 없습니다. 미리 정한 기준은 "하한이 −0.05 이상이면 많이 나빠지지 않았다"였고, −0.048이 이 기준을 넘었습니다 ([evaluate.py:259-262](../../../cluvi/evaluate.py#L259)).
</details>

<details>
<summary>Q8. HAWK 해설 페이지에 "질문 약 1,330토큰"이라고 적혀 있는데 test에서는 1,542입니다. 왜 다를까요?</summary>

질문 범위가 프롬프트 전체이고, 프롬프트에는 **리뷰 본문(최대 1,500자)**이 들어갑니다. 1,330은 dev 5건의 값이고, 1,542는 test 185건의 중앙값입니다. 리뷰 길이가 다르기 때문입니다.
</details>

## 8. 서비스로 가는 길 (E1·E2 정리)

```
서버 시작
  QwenVLM("heavy")                         models.py:110
    ├─ 공식 bf16 가중치 → LLM만 NF4 4bit    models.py:123-128
    └─ (E2) configure_model(keep 0.20)     models.py:143   ← 한 줄, 저장 파일 없음
리뷰가 들어오면
  analyze(Sample) → Card                   models.py:238
    = 1단계 입력 → 2·3단계 generate → 4단계 parse_vlm
상담원 화면
  Card: category / part / visibility / boxes / evidence
```

- **E1**: 따로 만들어 둘 결과물이 없습니다. 공식 가중치와 우리 프롬프트 파일 하나면 됩니다.
- **E2**: E1에 한 줄을 더합니다. 카드가 18% 빨리 나오지만 박스가 약해집니다.
- **E3**(다른 채팅에서 진행 중): LoRA 어댑터 파일이 하나 추가됩니다. [models.py:145-152](../../../cluvi/models.py#L145)에서 이미 그 자리를 만들어 두었습니다.
