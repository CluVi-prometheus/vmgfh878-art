Qwen 베이스라인과 HAWK

E1(Qwen2.5-VL-7B 제로샷)과 E2(+HAWK)를 어떤 틀로 돌리는지, 칸마다 무엇을 어디서 가져왔고 왜 그렇게 정했는지 한 장에 모았습니다. 뒤쪽은 HAWK 알고리즘을 원본 코드 기준으로 풀고, 나중에 우리 식으로 고칠 수 있는 자리를 짚습니다.

HAWK: 어떻게 토큰을 고르나

한 줄 요약: LLM 첫 층에 들어가기 직전, 글(질문) 토큰이 각 사진 토큰을 얼마나 "쳐다보는지"를 잰 뒤, 미리 구해 둔 헤드별 중요도로 가중해 점수를 매기고 상위 20%만 남깁니다. 나머지 27층은 짧아진 시퀀스로 돕니다. 학습이 없고(training-free), 리뷰마다 한 번(prefill 때)만 고릅니다.

식 한 줄

점수(j) = Σh=1..28 wh · L2정규화h( (1/|T|) Σt∈T qh,t · kh,j / √128 )j  →  상위 ⌈0.20·V⌉개의 j만 남김

T = 글(질문) 토큰들, j = 사진 토큰, h = 어텐션 헤드, wh = 미리 구한 헤드 중요도. 코드: src/hawk/pruning.py의 compute_hawk_scores · select_keep_indices.

헤드 중요도 28개 (저장소 config.py에 들어 있는 값)

원래 값(합 1.26)을 합이 1이 되게 나눈 값입니다. 1번 헤드 혼자 0.238로 전체의 4분의 1에 가깝고, 0번이 0.069, 26번은 0입니다. 논문은 이 값을 "헤드를 하나씩 꺼 보고 벤치마크 점수가 얼마나 떨어지는지"로 구했습니다(헤드 제거 실험). 이 값을 구하는 스크립트는 저장소에 없고 숫자만 들어 있어서, 우리는 이 숫자를 그대로 씁니다.

원본 코드 지도 (읽는 순서)

  1. scripts/patch_transformers.py — transformers 4.52.0 사본의 두 곳에 문장을 끼워 넣음. ① modeling_qwen2_5_vl.py: LLM에 넘기기 직전에 prune_qwen_prefill 호출 (첫 prefill에만). ② generation/utils.py: prefill 뒤에 짧아진 길이로 장부 정리 (input_ids, attention_mask, cache_position, 위치 보정값 rope_deltas, 최대 길이)
  2. src/hawk/config.py — HawkConfig (keep_ratio, 헤드 가중치, 정규화 방식, 최소 토큰 수). 설명에 "고정 1008 해상도는 0.198, 원본 해상도는 0.20" → 우리는 사진 크기를 그대로 쓰니 0.20
  3. src/hawk/integration.py — configure_model(model, HawkConfig(...)): 모델에 설정을 달아 두기만 함. 안 부르면 패치된 부분은 그냥 지나감
  4. src/hawk/pruning.py — _query_indices(질문 범위 찾기) → compute_hawk_scores(③~⑤) → select_keep_indices(⑥) → prune_qwen_prefill(전부 묶고 위치값 · 마스크를 같이 잘라 냄)

무엇이 빨라지나

  • LLM prefill: 28층 전부가 약 3,500토큰 대신 약 1,800토큰을 처리 (평균 리뷰 기준 약 절반). E2의 이득은 여기서 나옴
  • 디코딩: 앞에 쌓인 KV 캐시가 짧아져 토큰 하나 만드는 비용이 조금 줄어듦. 다만 출력 약 300토큰을 만드는 시간이 E2E의 대부분이라 E2E에서는 효과가 묻힘
  • 비전 인코더: 그대로. 토큰을 고르는 곳이 ViT 뒤라서 ViT 비용은 안 줄어듦 (해상도 낮추기와의 차이). E0 실측: prefill 1.9~6.9초 중 비전 인코더가 0.8~4.8초(60~70%) → HAWK가 줄일 수 있는 건 나머지 LLM 부분뿐이라, prefill 단축은 생각보다 작을 수 있음
  • 메모리: 점수 계산(28헤드 × 1,360 × 2,095 ≈ 8천만 칸)이 잠깐 메모리를 쓰지만, E0 실측으로는 최대 메모리가 오히려 0.7GB쯤 줄었음 (KV 캐시가 짧아진 효과가 더 큼)
  • E0 실측 (dev 5건): prefill 3.96 → 3.19초처럼 약 20% 단축. 비전 인코더 2.45초는 그대로이고, LLM 부분만 약 1.5 → 0.7초로 절반

HAWK의 뼈대(0층에서 글→사진 점수 → 상위 k)는 두고, 아래 손잡이를 하나씩 바꿔 가며 E2와 짝지어 비교하면 됩니다.

질문 범위 좁히기

지금은 지시문 전체 1,360토큰이 질문입니다. 리뷰 글만, 또는 주 불만 문장만 질문으로 쓰면 리뷰마다 다른 곳을 보게 됩니다. 고칠 곳: _query_indices.

잴 것: 같은 유지율에서 Group6 F1, 정답 박스 안 토큰을 얼마나 남겼는지(박스 덮음 비율)

사진별 몫 보장

여러 장을 한데 모아 고르면 한 장이 몫을 다 가져갈 수 있습니다. 사진마다 최소 몫을 주고 나머지를 점수로 나누는 방식. 고칠 곳: select_keep_indices.

잴 것: 사진 2장 이상 리뷰에서만 쪼개 본 성능

우리 데이터로 헤드 중요도 다시 구하기

지금 28개 숫자는 일반 벤치마크에서 구한 값입니다. silver 데이터로 헤드를 하나씩 꺼 보며 다시 구하면 결함 찾기에 맞는 가중치가 됩니다. 7B 0층은 28번 끄는 실험이면 됩니다.

주의: val · test는 이 계산에 쓰지 않음

리뷰마다 유지율 바꾸기

글만으로 판단되는 민원(맛 · 배송 등)은 사진 토큰을 더 버리고, 국소 결함은 더 남기는 방식. 텍스트 모델의 "사진 필요 여부" 확신도와 연결되어 나중에 cascade와도 이어집니다.

잴 것: 평균 유지율이 같을 때 고정 20%보다 나은지

공부 순서

  1. 28픽셀 = 1토큰: 위 표의 4,000 × 3,000 사진을 손으로 계산해 보기 (비율 유지 → 28의 배수 → 41 × 30)
  2. 모델이 실제로 받는 글: E0 0번에서 찍은 템플릿 결과에서 시스템 프롬프트 · "Picture N:" · 사진 자리(<|image_pad|>)를 찾아보기
  3. HAWK 네 함수: pruning.py를 _query_indices → compute_hawk_scores → select_keep_indices → prune_qwen_prefill 순서로 읽기 (모두 합쳐 약 200줄)
  4. 실제 숫자 보기: E0 1-H 결과의 cost.hawk에서 원래 / 남은 시각 토큰 수, 질문 토큰 수 확인
  5. 논문: HAWK 3.3절(점수 식)과 표 5(지연 · 메모리), VisionZip 3.3절(prefill 정의)

서비스로 가는 길

  • E1 방식: 서버가 공식 가중치를 4비트로 불러 같은 프롬프트로 분석 카드를 만듦. 따로 만들어 둘 결과물은 없음
  • E2 방식: 위와 같고, 불러온 뒤 configure_model 한 줄을 더 부름. HAWK는 학습이 없어서 저장할 파일도 없음 (헤드 가중치 28개는 코드에 들어 있음)
  • E3에서 LoRA를 한다면: 학습 결과는 작은 어댑터 파일 하나 → HF 비공개 저장소에 올리고, 서버는 원래 모델 + 어댑터를 불러 씀
